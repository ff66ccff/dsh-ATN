## 2. 本轮要解决的核心问题

### 2.1 判据建立在未确立的事件顺序假设上

旧判据隐含假设「事件 sequence 顺序 = 底层事实的发生顺序」。seed 59 证明它**不成立**：`delivered` 的 sequence（287）晚于消费它的 `step/start`（285），因为 `delivered` 是**收据**，在输入记录并 flush 之后才提交。

**这是本轮的根因，也是必须最先解决的问题。** 任何以事件位置为判据的结论，都必须先说明该事件的 sequence 位置是否是底层事实的可靠代理。

### 2.2 失败类别必须先被证明可达，否则分类器无法自证

旧 brief 的 (ii) 类把「正常同一步的收据延迟」与「真正漏唤醒」混在同一个桶里，所以它**必然假阳性**，而正向对照也因此无法构造（第 7.3 条停止的直接原因）。

正确的做法不是放宽定义，而是**把混在一起的类别拆开**，并且**用故障注入证明每个「缺陷类」确实可达**——只有被证明可达的类别才能作为分类器的一支。

### 2.3 上一轮未完成的交付项仍然欠着

旧 brief 的 4.3（完整任务语义表）、4.5（全五 seed 末次动作与飞行状态）、4.7（和式门对照）、4.8（不稳定测试复现）**均未完成**，本轮继承。

## 4. 必须实施的项目

### 4.0 事件语义前置闸门（G0，**阻塞性，必须最先完成**）

要求：

- 对**每一个**将作为判据锚点或分类依据的事件种类，从代码确立并书面记录：
  - 它是**命令**（触发某事）、**状态变更**（某事已发生）、还是**收据**（某事已被确认）；
  - 它相对其命名的事实的**时序位置**：早于／同步于／晚于；
  - 它的 **sequence 位置是否是底层事实时间的可靠代理**；若不是，**正确的锚点是什么**。
- 至少必须覆盖：`mail.state`（`queued` / `delivered`）、`step/start`、`model.start` / `model.end`、`turn/start` / `turn/end`、`task.state`、`node.state`、`tool.start` / `tool.end`。
- 对**持久 session 文件**（`session.v4.jsonl`）与**遥测事件**两个来源，必须说明各自的可信边界与相互关系；上一轮正是靠前者才确立了 seed 59 的真实链条。
- 每一条语义结论必须给出**代码位置**，并尽量给出一个**可核验实例**（如 seed 59 / mail-10）。

验收测试：

- 断言语义表覆盖上述全部事件种类，每条含类别、时序位置、sequence 可靠性、代码位置。
- 断言表中有条目明确写出「sequence 位置**不是**可靠代理」并给出替代锚点（seed 59 已提供一个）。
- **断言在语义表完成之前不存在任何 seed 级判定输出**（可由脚本的产物结构或执行顺序断言）。

> ⚠️ **若发现任何判据所依赖的锚点语义无法从代码确立，立即依第 7.1 条停止并报告。不得用假定补齐。**

### 4.1 失败类别定义与可达性证明（G1，**阻塞性**）

要求：

- 从代码定义**互斥**的类别，至少区分：
  - **(a) 正常同一步收据延迟**：邮件在 `queued` 后进入某一步的输入，`delivered` 收据在该步期间或之后提交。**这不是缺陷。**
  - **(b) 输入已记录但模型请求从未开始**：持久历史中已有该邮件的输入记录，但没有对应的 `model.start`。
  - **(c) 持久收据缺失**：输入被记录，但从未提交 `delivered`。
  - 另需覆盖：**邮件在投递时接收者已 retired/failed**（不可达，不计入缺陷）。
- 每个**缺陷类**（即 (b)、(c)）必须通过**故障注入**证明其**确实可达**：构造一个确定性场景，使系统真实进入该状态，并断言分类器将其判为缺陷。
- 若某一类**无法被注入达成**，必须**删除该类别**并说明理由，**不得**保留一个无法自证的类别。

验收测试：

- 断言每个缺陷类都有对应的故障注入用例，且该用例真实进入该类状态（不是构造一个假的事件序列）。
- 断言 (a) 被显式标注为非缺陷，并有对应用例证明它**不会**被判为缺陷。
- 断言类别集合互斥且穷尽（每个已投递邮件恰属一类）。

### 4.2 锚点修正后的邮件生命周期追踪（G2）

要求：

- 锚点从 `delivered` 改为**实际造成唤醒的事件**（依 4.0 的语义表确定，基线显示为 `queued`）。
- 对每封邮件建立生命周期：`queued` → **包含该邮件的具体输入步**（由持久 session 的 user/message 记录 + `step/start` 的 time/turn/step 唯一连接）→ 模型请求（`model.start` / `model.end`）→ 准入结果 → 该步结束。
- 输出必须含**该邮件进入的具体步号**，而不只是「之后有没有步」。
- 关联规则必须显式声明：先限定既有 session 映射，再限定该邮件的 queued→delivered 时间区间与 `messageKind`，断言唯一连接；**不得**默默按「任务与邮件 1:1」连接（一项任务允许多封邮件）。

验收测试：

- 断言每封邮件的输出含「进入的具体 turn/step」或明确的「未进入任何步」。
- 断言 seed 59 / mail-10 被判定为 **(a) 正常同一步收据延迟**，而**不是**缺陷类。这是旧判据的致命盲点，必须作为固定用例。
- 断言关联规则被书面声明，且输出中每封邮件的连接都有唯一性依据。

### 4.3 二值判定与双向对照（G3、G4）

要求：

- 每个 seed 输出 `mechanism-gap` 或 `no-wake-eligible-work`，附**支撑条目**（哪封邮件／哪个任务／哪个 sequence）。
- **必须提供三类对照**：
  - **正向（缺陷）对照**：故障注入一个按实际代码**确实欠下推送**的状态，断言判为 `mechanism-gap`。
  - **负向（正常）对照**：seed 59 / mail-10 式的同一步收据延迟，断言判为**非缺陷**。
  - **不可达对照**：接收者已 retired/failed，断言计入不可达而**不**计入缺陷。
- 若分类器只能产出一种结论，上述对照必须失败。

验收测试：

- 断言三类对照各自通过。
- 断言真实五个 seed 的判定可由其支撑条目逐条人工复核。
- 断言 seed 59 在**修正后**的判据下不再产生候选（旧判据的唯一候选被消除）。

### 4.4 末次动作归因与飞行状态（G5，继承旧 4.5）

4. **邮件与节点的关联不可判定**（例如持久 session 的 `session` 无法与 `step/start` 唯一对应）。
5. **审计无法在 CI 重放且无法声明所需文件**。

**报告格式**：停在哪一条、实测证据（命令与输出）、已尝试的方案、建议的下一步。**不得补造证据。**
