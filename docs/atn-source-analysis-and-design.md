## 2. 已确认的源码事实

### 2.1 可以做真正的外部插件，不必 fork Harness

Harness 的模型、工具、会话、agent loop 本身都是 Cordis 插件。外部插件能注册服务、工具、提示词、事件监听和可清理资源。分发形式是带 `dsh.bundle` 声明和 `cordis.patch.yml` 的 npm 包；一个安装包可以包含多个插件入口。

参考：[架构](../upstream/deepseek-harness/docs/architecture.md)、[打包与安装](../upstream/deepseek-harness/docs/user/develop/basic/publish.md)。

对 ATN 的含义：不必重新实现模型调用循环，也不需要另起一个 Harness 可执行程序。先做一个安装包，内部按职责拆分即可。

### 2.2 核心 Agent 接口足够低层

`ctx.agents.create()` / `resume()` 返回由调用者持有的 `AgentHandle`。运行时所有权与持久化谱系是不同概念；`parentAgent` 是可选的运行时父节点。创建与恢复都支持在发布前通过 `setup` 完成节点配置。

现有 Agent 提供：

| 操作 | 源码语义 |
|---|---|
| `followup()` | 排到后续独立回合，并唤醒 |
| `steer()` | 运行时在下一步接收；空闲时唤醒 |
| `inject()` | 注入下一步上下文，但不唤醒空闲节点 |
| `cancel()` | 中断当前工作；可选择保留 inbox |
| `whenIdle()` | 等待整个 Agent 当前活动归于空闲，不是某一条消息完成的回执 |
| `AgentHandle.dispose()` | 停止、等待清理并释放运行时；不等于删除持久会话 |

参考：[创建、恢复及所有权](../upstream/deepseek-harness/packages/core/agent/src/index.ts)、[运行时接口](../upstream/deepseek-harness/packages/core/agent/src/runtime-types.ts)、[实际创建和清理](../upstream/deepseek-harness/packages/core/agent-loop/src/index.ts)。

对 ATN 的含义：原则上可以让网络运行时持有节点，而不是让创建者节点的存活决定后代的存活。但 Cordis 的调用方作用域确实参与所有权，不能只把一个 handle 放进 Map 就认为解耦完成。

### 2.3 原生 subagent 已经支持很多能力，但仍有父子语义

- 有 fresh spawn、历史 fork、一次性运行、可续聊运行和冷恢复。
- 同进程子节点能继承模型选项、preset、工具与提示词配置，也允许局部限制。
- 公共 `sendMessage()` 是邻接父子通信，不是任意同伴通信；向父节点发送还要求满足驻留和存活条件。
- 委派工具默认深度来自 `maxDepth = 1`，并非默认无限递归；工具可显式配置深度策略。
- 可续聊驻留池默认上限是 8。这不是全系统 token 预算，也不覆盖所有 provider 和一次性子任务。
- 可续聊节点有未处理 inbox 或仍拥有子节点时，不会自然释放驻留。
- 子节点不能因为有同样的工具，就自动获得独立升级权限的能力；委派会固化权限范围并将审批策略限制为 `never`。

参考：[subagent 说明](../upstream/deepseek-harness/packages/subagent/subagent/README.md)、[子节点配置与权限继承](../upstream/deepseek-harness/packages/subagent/subagent/src/child-agent.ts)、[驻留与回收](../upstream/deepseek-harness/packages/subagent/subagent/src/continuation-activation.ts)。

对 ATN 的含义：递归创建本身不是主要难题；非树状协作、独立寿命和统一资源限制才是。

### 2.4 实验性 Agent Teams 很接近，但不是同能力自治网络

已存在的 Teams 提供持久 roster、同伴消息、任务 DAG、CAS 任务更新、等待事件和恢复机制。但代码明确限制：只有 Lead 可以创建或中断成员，成员都是 Lead 的直接子节点，roster 不支持删除和名称重用。

消息投递采用先持久化队列，再投递目标 inbox，再记录送达的方式。目标会话保存消息 id 和发送者，重试时去重。实现是单进程协调，不是跨进程共识，也不能据此承诺外部工具副作用恰好执行一次。

Teams 的同伴投递还依赖 `@deepseek-ai/dsh-subagent/internal` 的 host adapter，并不只是调用公共 `sendMessage()`。

参考：[Teams 说明](../upstream/deepseek-harness/packages/experimental/agent-team/README.md)、[Lead 限制](../upstream/deepseek-harness/packages/experimental/agent-team/src/roster.ts)、[mailbox](../upstream/deepseek-harness/packages/experimental/agent-team/src/mailbox.ts)、[内部投递 adapter](../upstream/deepseek-harness/packages/subagent/subagent/src/internal.ts)。

对 ATN 的含义：借鉴消息可靠性和恢复设计；不直接把 Teams 的角色与任务管理制度当成 ATN 基础。

### 2.5 模型输入必须可回放，网络元数据不必全部进入上下文

Harness 要求实际模型输入能由 Session 日志重建。`session/event` 是持久事实；`agent/*` 是运行期事件。工具结果、接收到的消息和实际使用的动态上下文应走已有记录路径，而非在发请求时偷偷拼接。

非对话的网络成员、租约和待发信箱可以使用 `ctx.storageDomain`。它支持 schema 校验、顺序写入以及写成功后的持久保证，但不是跨记录、跨 Session 的分布式事务。网络记录到目标 Session 的交接仍需要幂等恢复协议。

参考：[Session 与扩展点](../upstream/deepseek-harness/docs/architecture.md)、[storage-domain](../upstream/deepseek-harness/packages/storage/storage-domain/README.md)、[工具接口](../upstream/deepseek-harness/docs/cookbook/adding-a-tool.md)。

## 3. 建议的核心定位

> 同构的能力，不同的局部上下文；由局部协作形成动态网络，由确定性运行时保证资源、权限和消息可靠性。

“相同能力”建议定义为：同一模型配置、同一套基础工具、同一套 ATN 操作和同一套行为规则。不要求每个节点拥有相同知识、相同任务，也不代表允许节点绕过人类授权。

第一版不预设 planner、researcher、reviewer、executor 等固定角色。某个节点可以暂时负责审查，但这是收到的任务，不是一个永远不能派生节点的受限身份。

人类输入和最终输出需要入口，但入口节点不是唯一有派发权的智能主管。入口的特殊性是连接用户，不是拥有更强的网络能力。

## 4. 三种关系必须分开

### 创建谱系

记录谁创建了谁，用于审计、预算归因、失败诊断和局部邻居推导。它自然是树或森林，但不等于完整的通信网络。

### 协作通信与四个邻居位置

已确认：每个节点最多取两个上游邻居和两个下游邻居。初始对应父、祖父、选定子节点及该分支的孙节点。允许创建多个子节点，但只选择一条下游分支，不把所有子孙都纳入审批集合。

第一个成功创建的子节点自动成为 `selected_child`，后来创建的子节点不自动替换它。所选邻居退出拓扑时，根据既有拓扑向更外层自动连接和补位。出生关系始终保留，向外补位不重写 `creator_id`，也不迁移任务、历史或资源所有权；补位后的上游/下游邻居不一定还是出生意义上的父/子。

对“更外层”的当前实现解释是沿既有方向延伸：向上沿出生祖先路径，向下沿已选分支，跳过已经退出新工作拓扑的节点，分别取最近两个仍接收新工作的节点。退役节点的路径记录应保留，才能继续找到更外层节点。若该方向走到尽头，则先留空，不未经定义跨到其他出生分支或全网随机补位；这一尽头处理是实现默认建议，不是用户已明确选择的规则。

其他节点仍可以通过按需发现成为通信伙伴，但不因发过消息就自动成为邻居或审批者。通信伙伴集合与参与共享文档审议的邻居集合分开；历史消息不因补位而删除。

在允许分叉且只选择一条下游分支的条件下，邻域不保证对称：A 创建 B、C 并选择 B 时，C 的父邻居仍是 A，但 A 的子邻居不是 C。运行时不能自动补反向关系把四个名额扩成更多。

节点准备退休时先退出新工作拓扑，邻居立即向外补位；节点仍负责退出前已经分配给它的任务和提案审议。新提案使用新邻居，旧提案保留原审批者。投票资格由提案的持久名单决定，不能因为节点已不在当前邻域就拒绝它对旧提案的投票。

自适应发生在任务分解、节点创建、按需联系、退出和自动向外补位中，不必随意改变四个位置的定义。实际形成的通信网络仍需与固定拓扑作等预算比较，不承诺增加消息或分支就产生更好的群体效果。

### 运行时所有权

ATN Runtime 持有节点运行资源。创建者结束工作，不默认杀死仍有价值的后代；用户停止整个网络时，才由网络所有者统一停止和等待清理。

这一层可以是单进程集中实现。基础设施集中不等于必须有一个负责全部推理和分工的中心 LLM。

## 5. 面向节点的最小操作

建议保留四个基础协作工具，并为共享目标文档增加两个明确的审议操作，不把它们混成一个通用的多 action 工具：

| 工具 | 目的 |
|---|---|
| `atn_spawn(task, context, lease)` | 创建同能力节点，交给它一个可交付的小问题；指定受限寿命 |
| `atn_send(to, message, reply_to?)` | 向已知同伴发送异步消息，保留线程关系 |
| `atn_peers(query?)` | 查询局部邻居或按当前任务描述发现现有同伴；返回有界结果 |
| `atn_finish(summary)` | 请求正常退休：先停止接收新工作并触发邻居补位，结清已承担任务和审议后再释放 |
| `atn_propose(base_revision, change, reason)` | 提交共享文档修改，运行时固定提案内容和审议邻居集合 |
| `atn_vote(proposal_id, decision, reason?)` | 对自己收到的确切提案明确同意或反对，运行时记录真实投票者身份 |

完成一个局部任务后，节点默认等待新任务，可由消息唤醒；这不同于请求退休。`finish` 请求进入第 8 节的正常退出流程，不立即销毁 Agent，也不让它反复轮询其他节点。

已确认寿命可以按任务需要续期。`lease` 的具体字段和续期接口仍属实现设计：可表达正常退休时限和工作额度，并受用户配置的网络预算约束；恢复或续期不能重置已消耗额度。正常退休与用户全局停止、硬预算耗尽必须区分，后两者不保证继续完成任务。

这些是拟议工具名称，不是 Harness 已有接口。尤其 `finish` 不能在工具执行栈内等待销毁自身；节点要先返回该调用，并在已承担工作安全结算后由运行时释放。

## 6. 建议给模型的少量行为规则

1. 每次聚焦一个明确、可验证的局部结果；问题太大时拆出一个小问题。
2. 需要帮助时优先联系已有相关节点；没有合适节点且预算允许时再创建。
3. 向需要它的节点传递结论、证据引用和未解决问题；不广播完整对话，不为礼貌确认反复唤醒对方。
4. 完成局部任务后等待新任务，不轮询维持存在；决定退休时停止接收新工作，完成已承担任务和旧提案审议后退出。
5. 需要修改共同目标文档时提出变更并交给邻居审议；审批条件满足之前，继续以当前生效版本为准。

规则简单是模型侧目标，不意味着运行时可以没有一致性、权限和资源约束。复杂性应收在一个有小接口的深模块中，而不是推给每个节点记住几十条协议。

## 7. 信息传递

### 全局共享目标文档

已确认的方向：所有节点读取同一份简短的总体目标和成功标准；每个节点只持有自己的局部任务与必要上下文。共同目标由网络级持久化共享文档承载，不依赖出生者或某个 Lead 的存活。

建议把它设计为一份短 Markdown 文档，由 ATN Runtime 管理版本化持久记录；Markdown 是内容和展示形式，不意味着所有节点直接覆盖同一个普通工作区文件。物理存储位置和编辑入口尚未定案。

文档初始内容建议只包含：

- 总体目标：网络最终要交付什么。
- 成功标准：哪些可观察结果足以验收。
- 共同约束：不能违反的范围、限制和明确非目标。

不在这份文档中持续累积所有成员、子任务、进度和聊天，否则局部信息原则会被一个不断增长的全局上下文架空。需要共享的具体成果仍通过消息和稳定产物引用传播；将来若需要共享成果索引，应与目标文档分开。

Agent Teams 可借鉴的是共享任务板的版本化持久状态，而不是已经存在的全局目标 Markdown 文件：[TeamJournal](../upstream/deepseek-harness/packages/experimental/agent-team/src/journal.ts) 按 Team 串行化写操作，flush 后通知；[TeamTaskBoard.update](../upstream/deepseek-harness/packages/experimental/agent-team/src/task-board.ts) 检查 `expectedRevision`，旧版本写入明确失败。ATN 可复用这些设计原则，但不照搬 Lead Session 作为唯一存储所有者，也不把版本检查误当成修改权限检查。

拟议文档接口由运行时负责网络身份、当前版本、正文、修改者和历史。写操作携带预期版本；并发冲突要求重新读取，不采用最后写入覆盖。持久化成功之后才公布新版本；存储失败不得向节点宣布更新成功。`storageDomain` 可承载该状态，但版本历史和恢复协议仍需 ATN 自己定义，不能假设跨记录事务已经存在。

节点创建或恢复时自动获得完整的短文档快照。后续在新的模型请求准入时检查版本，仅在变化时同步并记录新快照，不需要节点反复调用 read 工具。每次请求绑定具体版本；正在进行的请求不会被追溯修改，后续请求采用新版。变化通知不为了同步版本而唤醒全部空闲节点。

模型实际读到的版本号与正文必须进入该节点的 Session 可回放输入，不能只记录一个会随时间变化的文件路径。新目标与旧局部任务冲突时，节点应重新判断任务，而不是继续把旧任务当作现行目标；涉及权限撤销或全局停止的变化仍由运行时立即执行，不依赖模型稍后读到文档。

### 邻居审议后的自主更新

已确认：节点可以在执行中自主修改全局共享目标文档，但必须得到该节点的全体邻居明确同意；不采用多数票，也不要求用户逐次确认文档修改。该机制是局部一致同意后产生全局可见的文档版本，不是全网表决，也不是某个 Lead 审批。

全体一致同意、四个邻居位置、退出后向外补位，以及新旧提案分别由新旧邻居处理已经确定。以下协议据此细化，版本冲突、超时和崩溃处理仍为实现建议：

1. 提案者提交基于文档版本 `r` 的完整修改内容或补丁及理由。运行时分配提案 id，并固定提案内容、基础版本和当时的有效邻居集合。
2. 审议邻居由运行时从当前两个上游和两个下游位置取得，并在分配时持久固定。节点开始正常退出后，新提案分给补位后的邻居，旧提案仍由原节点审议；以分配记录而非消息实际送达时间区分新旧。投票检查固定名单，不要求原审批者仍在当前拓扑中。内容修改必须成为新提案。
3. 仅向这些邻居发送审议请求。邻居可以被这项具体工作唤醒，但不广播给全网；邻居审查确切版本上的变更，通过结构化操作明确同意或反对。普通聊天中的“可以”、超时和沉默不算赞成，提案者不能代投。
4. 满足审议条件后，运行时检查当前文档仍为版本 `r`，才持久提交 `r+1`，保留相应提案与审批依据，再通知成功。若其他提案先改变了文档，本提案过期；重新基于新版本提案和审议，不自动合并或复用旧票。
5. 反对、过期或超时都保持原文档不变。正常退出的节点继续完成旧提案审议；崩溃或强制停止不能假定还能投票，旧提案只能等待原节点恢复，或到期失效后按新邻域重新提出，不能转移或伪造其票。无邻居不视为自动通过。初始文档从用户任务建立属于网络初始化，不是无邻居节点的自主修改。

邻居关系参与修改授权，不能仅由最近聊天或发现结果推断。邻居推导见第 4 节，正常退出见第 8 节。退出与提案分配必须有唯一的先后裁决点，避免节点被划为退出后又承担未记录的新审议。文档版本、审议名单和每张票都应可持久恢复并去重；正常退出不能丢掉已确认的票，网络硬停止也不能被迟到投票绕过。

此机制只保证规定邻居对规定修改表示同意，不证明结论正确、赞同者相互独立，也不等于分布式共识。版本冲突检查阻止旧内容覆盖新版，不解决不同局部群体依次修改目标的语义分歧。宿主权限、网络预算和用户全局停止不因共享文档被修改而扩大或失效。

### 独立上下文，显式共享

默认 fresh context：共享基础能力和规则，但只传当前子问题、必要证据引用和联系地址，不自动复制创建者全部历史。需要 fork 时作为明确选项评估，避免上下文污染和高度相关的错误。

消息优先携带简短结论和可复查的文件、事件或产物引用。引用必须标明具体版本或稳定标识；指向不断被覆盖的文件不能作为可靠证据。

### 最小 envelope

运行时补充 `network_id`、`message_id`、真实 `sender_id`、`target_id`、可选 `reply_to`、正文和证据引用。模型不自行填充可信发送者身份。

不先强迫所有消息采用复杂的任务本体，也不把一个全局共享对话塞进每个节点上下文。共享任务板和发布订阅不是第一版前置条件。

### 已确认的局部任务执行方式

每次聚焦一个局部任务，消息异步到达，在安全步界处理；用明确的请求/回复标识关联结果，传输回执不等于业务完成。审议是普通节点承担的有界协作工作，不另设永久审核角色，也不要求节点掌握全局任务板。

### 交付语义

先持久化待发消息，再尝试投递；忙节点在安全步界接收，空闲节点按需唤醒。按目标串行入队，同一稳定消息 id 去重。正常退出中的节点只接收退出前已有工作的关联消息和审议，拒绝新任务；完全退休或失败的目标必须有明确结果，不能无限静默排队。普通信息、正式任务请求和结果需要有可区分的语义，不能从自由文本猜测生命周期义务。

“已存入信箱”“已进入模型上下文”“已完成对应工作”是三件不同的事。传输确认不算工作完成；需要完成确认时，用显式结果消息和 `reply_to` 关联。

保留 sender、message id、原始证据链，避免同一结论被转发三次就被当作三份独立证据。跨节点文本不是人类授权，也不是新的系统指令。

### 背压

限制消息大小、每节点积压和唤醒频率，批量交付短时间内的消息。传输回执由代码处理，不要求模型礼貌回复。过载要返回明确结果，不丢弃已承诺持久的消息。

## 8. 生命周期与资源

区分节点的逻辑寿命、当前工作活动和运行期驻留。已确认：完成一个局部任务后等待新任务，寿命可以按任务需要续期；正常退休前先完成已经属于自己的工作。这里将“完成后再退休”解释为正常退休时先结清旧工作，而不是每完成一个任务就立即销毁。

正常退出需要两个阶段：先退出新工作拓扑，再释放运行资源。拟议状态如下，状态名属于实现选择：

| 生命周期阶段 | 新任务与新提案 | 已承担工作 | 拓扑与资源 |
|---|---|---|---|
| `active` | 可以接收 | 正常执行 | 参与邻居推导；工作活动可为运行或等待 |
| `draining` | 不再接收 | 继续原任务、关联结果和旧提案审议 | 新拓扑绕过它向外补位，但保留处理旧工作的能力 |
| `retired` | 不接收 | 已结清，或记录硬停止/失败结果 | 释放 Agent，保留身份、谱系、分支路径和历史 |

工作活动的运行/等待与上述生命周期分开：空闲节点仍是活跃邻居，可以被任务和投票请求唤醒；正在正常退出的节点也可能等待自己已有任务的结果。新拓扑绕过的应是退出节点，而不是所有当前没有调用模型的节点。

寿命续期依据剩余任务需要，在网络资源预算内处理。正常退休时限不能等同于硬截止时间，否则既无法完成旧任务，也无法保证旧提案继续由原节点处理。正常退出不级联销毁后代，不把旧任务或旧票转给补位邻居。

节点完成自身审议并把投票持久化后，该项义务即可结清；后续提案提交由 Runtime 托管，不必让投票节点为了等待其他人的票而一直驻留。任务是否完成也不能仅凭 `idle` 判断，原型需有最小的任务请求、结果和审议义务记录；这不要求给模型增加全局任务 DAG。

第一版可让等待和正常退出中的节点保持轻量驻留，以减少冷恢复复杂度；后续可用同一 Session 身份进行冷恢复。退出、任务/提案分配、消息投递和资源释放必须共享明确的提交次序，避免新任务落在已停止接收的节点，或旧审议被错误拒收。

建议的硬限制：网络最大并发、累计创建上限、网络总期限、每节点工作额度、消息容量。只限制并发不够：串行地创建无限节点一样会花无限费用。

token 与费用需要持续统计。不能把 `maxTokens` 当成网络总预算，它只是单次请求输出上限。硬 token 预算需要请求前预留、结算和重试/辅助模型调用归因；未实现这些前，只能报告实际计量与近似限制。

用户全局停止、硬预算耗尽、正常退休和单次调用失败分别记录。用户停止或硬资源限制可以中断未完成工作，必须如实记录，不承诺仍能完成旧任务或投票；正常退休则先完成旧工作。到期本身不是成功，停止后不得通过重试、续期或新消息悄悄复活节点。

权限和沙箱由 Harness 的现有机制继续执行。ATN 若绕过原生 subagent 管理器直接创建 Agent，必须显式保留委派权限限制，不能因没有父节点就把工作提升为全权人类会话。

## 9. 收敛与群体效果

没有消息、没有运行节点，只能判断网络暂时静止，不能证明目标已经完成。它也可能是所有节点互相等候、子任务失败或验收标准缺失。

已确认保留明确的人机交付入口，汇总由一个同能力普通节点承担，不赋予它独占的派发或指挥权。任务入口携带成功标准；结果应指向测试、文件、可复核推导或其他证据，按当前生效目标版本验收。承担汇总的节点给出回答不等于其他节点已结束，网络仍需完成关闭和清理。

运行时区分完成、失败、预算耗尽和停滞。无可运行工作且目标未完成时应报告停滞，而不是无限唤醒全网让节点聊天。

同模型的错误可能高度相关，多数赞同不是正确性的证据。允许按需产生反例检查和独立验证任务，但不要先把固定“审核主管”写死。

## 10. 推荐的落地方式

### 外部安装包

`dsh-atn` 作为可安装 bundle。内部先有三个职责清楚的模块：

- **ATN Runtime**：身份、成员、通信、运行资源、寿命、预算和恢复。
- **ATN Tools / Policy**：少量工具、统一提示词和节点 preset。
- **ATN Observation**：从已记录事实派生状态、创建关系、协作关系和费用；第一步日志即可，之后再接 Web UI。

不要求一开始拆成三个 npm 包，也不先设计多个虚构 backend adapter。

### 复用与自行拥有的部分

复用 Harness 的 Agent factory、agent loop、模型路由、工具执行、Session persistence、scoped preset、权限沙箱、storage-domain 和现有可观察事件。

ATN 自己拥有网络成员资格、消息 envelope 与 outbox、非树状路由、网络级生命周期和资源分配。网络元数据使用独立持久域可以避免将唯一存储所有者绑定到一个必须永远存活的 Lead；真正送入模型的信息仍记录在对应 Session。

借鉴 Teams 的持久入队、目标去重和失败可见设计，不直接依赖其 Lead-only 服务。也不把 `/internal` 的 host 投递接口作为长期插件接口。

### 需要先验证的三个源码接缝

1. 从 ATN 自有 Cordis scope 创建节点，确认创建者退休不会撤销其他节点的资源，插件卸载又能彻底清理全部资源。
2. 创建与恢复时安装同一 preset 和受限授权，确认所有节点能递归调用 ATN 工具，而任何节点都不能借 ATN 绕开预算或升级权限。
3. 持久消息与 Session inbox 交接，覆盖投递、回合拒绝、中断、退休、恢复间的竞态；确认不会把传输回执误判成业务完成。

网络作用域所有权、独立节点释放、同构原型工具、旧审议续办和可控重建已由真实内核原型演练验证。正式 preset、权限继承、完整 profile 装配和崩溃恢复仍未验证；具体证据和不能外推的范围见 [原型验证报告](atn-prototype-validation.md)。

## 11. 建议的第一轮实验

先做单进程、同模型、小网络。规模如 3–8 个节点仅是实验参数，不是固定产品上限。先用只读分析或写入不同产物的任务隔离拓扑效果，随后测试多人修改同一代码库。

对于代码编辑，消息协议不会自动解决文件冲突。第一轮选择不重叠写入目标；正式支持并行改同一文件前，需选择隔离工作区加合并，或真正执行的写入协调机制。仅在提示词中写“不要冲突”不算解决。

使用相同模型、相近总 token / 费用预算和同一验收标准比较：

- 单 Agent。
- 固定父子树。
- ATN 动态同伴网络。

记录正确率、任务完成率、费用、耗时、消息 token 占比、重复工作、无效唤醒，以及实际联系如何变化。多跑几个任务和随机种子，不把一次成功演示当成群体智慧证据。

运行时测试使用确定性模型替身：A 创建 B，B 创建 C，A 结束职责，B/C 仍能协作；B 与非父节点交流；节点满额时有界拒绝；恢复不重置预算；退休和投递竞态不吞已确认消息；循环等待不被判定为成功；卸载不留下运行任务。

共享文档协议还需测试：投票绑定确切提案与版本；提案后拓扑变化不替换审批名单；未满足审议条件不能提交；旧版本提案不能覆盖新版；失败和超时保留原文档；恢复不丢失已确认投票、不重复提交；网络停止后不因迟到投票提交变更。投票测试明确覆盖全体同意可进入提交检查、任一反对不能通过、任一未表态不能通过；多数赞成不能替代全体同意。

## 12. 已对齐原则与后续问题

### 已确认：出生关系不构成执行从属关系

2026-10-03，用户确认：**“子 agent”只是出生关系，具体执行时各个 agent 是相互独立的个体。**

据此，创建谱系记录来源并按第 4 节参与邻居选择，但不构成执行控制或级联终止，也不要求消息逐代转发。每个节点独立执行；创建者结束职责不代表其创建的节点也结束。网络仍受用户授权、预算和全局停止控制。

实现方向：由 ATN Runtime 而非出生者的运行作用域持有节点生命周期；节点使用稳定独立身份，出生者使用 `creator_id` 记录。已确认寿命可根据任务需要续期，正常退休先结清已有工作；独立执行不意味着无限寿命或任意控制同伴。具体续期接口和资源计量在原型设计中确定。

### 已确认：局部信息、按需发现，面向蜂群式网络

2026-10-03，用户确认偏好：**节点依靠局部信息、按需发现同伴，整体呈现类似蜂群的网络。** 不向每个节点默认提供全体成员及其当前任务；邻域按后续确认的四个位置规则形成，节点仍可按需发现其他通信伙伴。

蜂群在这里表达同能力独立个体通过局部交互形成协作，不意味着已经决定采用生物仿真算法、信息素机制、跨进程分布式部署或特定图结构。

### 基于上述原则的建议，尚未定案

- 节点只持有当前任务、必要证据、少量已知伙伴和收到的消息；发现同伴时获取有界的公开摘要，不读取对方完整上下文。
- 发现优先复用已知伙伴，再按需返回少量新候选。发现本身由确定性运行时执行，不唤醒所有节点，也不引入一个全局 LLM 调度者。
- 出生关系建立初始联系，不限制后续协作。未知节点应仍可被发现，避免局部网络永远困在互不连通的小群体中。
- 第一次实现先验证局部决策产生的动态协作，不提前加入全局拓扑优化、复杂信誉评分或信息素规则。

### 已确认：通过持久化全局文档共享目标与成功标准

2026-10-03，用户确认：**所有节点知道同一份简短的总体目标和成功标准，但只持有自己的局部任务与必要上下文；共同目标通过持久化全局共享文档实现，可参考 Agent Teams。**

共享文档属于整个网络，不引入固定 Lead 或全局任务调度者。拟议内容、版本更新、模型读取和持久化方式见第 7 节。

### 已确认：节点修改共享文档须获全体邻居同意

2026-10-03，用户明确允许节点在执行中自主更新共享文档，并进一步确认必须得到全体邻居同意。多数票不足以通过；此前建议的逐次用户确认不再采用。

第 7 节提出固定邻居快照、明确投票和版本化提交的最小协议。全体邻居同意、新提案由新邻居审议及旧提案继续由原邻居处理已确认；版本冲突、超时和崩溃处理仍属实现建议。

### 已确认：四个邻居位置，允许分叉但选择一条下游分支

2026-10-03，用户指定邻居为父节点、祖父节点、子节点和孙节点，并在分叉问题上选择“允许分叉，选一条分支”：最多四个邻居，子、孙来自选定的一条下游分支；其他分支不自动进入该节点的审批邻居集合。

出生谱系参与邻域选择，但仍不构成执行从属或级联销毁关系。每个节点记录一个 `selected_child`，初始沿所选路径取得子、孙邻居，分叉下的邻域不保证对称。用户进一步确认第一个成功创建的子节点自动选中，后来创建的不自动替换；邻居退出后根据拓扑自动连接更外层节点。具体路径解释及路径尽头的默认建议见第 4 节。

## 13. 本轮确认的运行规则与原型范围

2026-10-03，用户对此前四组问题给出选择：

1. 完成局部任务后等待新任务；寿命可以续期，由任务需要决定；正常退休前完成属于自己的任务。邻居退出后根据拓扑自动连接更外层节点，新提案交给新邻居，旧提案继续由原节点处理。
2. 第一个子节点自动选中，新建子节点不自动替换；所选邻居退出时根据拓扑自动切换到更外层节点。
3. 接受每次聚焦一个局部任务、异步消息在安全步界处理、用请求/回复标识关联结果，不设置复杂任务板或永久审核角色。
4. 接受明确的人机交付入口，由同能力普通节点汇总而不垄断指挥；完成、失败、停滞和预算耗尽分别报告，不以全网空闲作为成功证据。

这些决定要求正常退出分为“停止接收新工作并从新拓扑移出”和“完成旧工作后释放”两个阶段。该实现解释及硬停止例外见第 8 节；新旧审议交接见第 7 节。

### 原型应验证的完整路径

- 同能力节点递归创建并独立工作，多个子分支不因创建者退出而终止。
- 首个成功子节点初始化所选分支，后来创建的分支不自动替换；根据当前拓扑导出至多两个上游和两个下游邻居。
- 已选路径的中间节点开始退出后，其他节点自动连接更外层节点，出生来源保持不变。
- 已完成局部任务的节点等待新任务；正常退休中的节点不接新任务，但继续完成原任务和原审议。
- 退出与提案分配并发时，一份提案始终使用唯一的审批名单；新提案交给补位邻居，原节点对旧提案的票仍有效。未全票通过绝不能提交。
- 原节点投票持久化并结清工作后可释放，Runtime 继续持有提案；恢复不重复投票或提交，硬停止不被续期或迟到投票绕过。
- 结果按当前目标版本验收并交付，剩余工作得到明确结算；空闲、失败和预算耗尽不冒充完成。

### 实现层面仍需落实的细节
