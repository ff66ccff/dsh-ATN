## 1. P0：动态出度下的结构证明重导

**现状。** 拓扑层有第 5 轮测量及后续 `topology-binding-proof`、参考执行和测试证据；这些是绑定具体 fixture/静态选边/额度的结构性质，不是任务质量优势。B 已用纯计算脚本重导 seed 17/31/45/59/73，见 [B 报告](DYNAMIC_DEGREE_IMPLEMENTATION_REPORT.md)。

**核查结果。** 历史二边实验显式冻结天花板2，默认八节点 wide 仍为4；两类既有证明输入/结论/资格均无翻转。不能因为默认天花板变8就宣布所有旧证明失效。N>8 的默认曲线并未获得通用结构证明，若新增相应比较或宣传，必须先设计并重导相同条件的夹具。

**范围决策。** 既有五 seed 复核本轮已完成，不回退 B；更大规模补证作为条件任务，不挤占威胁模型与宿主策略一致性验证。保留脚本作为 CI 工件。

**交付物。**
- 在动态曲线下重算每个 seed 的可达性结论，**逐 seed 给出与旧证明的一致／不一致**。
- 明确哪些 seed 在新曲线下**不再**满足「固定拓扑不可达」——这些 seed 必须退出任何后续比较。
- 一个可在 CI 重跑的纯计算脚本。

**风险。** 若新曲线下大量 seed 的结论翻转，说明「动态出度」与「拓扑绑定」两条线的兼容性需要重新评估——**必须在实施前知道，而不是实施后**。

## 2. P0：威胁模型与信任边界

**现状。** [README](../README.md) §3 用散文列出了 4 条「不防」（推理衍生、物理侧信道、合谋互通、网络外动作）。[13 条出站通道审计](information-boundary/OUTBOUND_CHANNEL_AUDIT.md) 列出了通道与拒绝码。

**缺口。** 缺一份**形式化的威胁模型**：对手是谁、具备什么能力、信任边界在哪、假设是什么、哪些在范围内、哪些明确不在。散文式的「不防」列表无法被审计方引用，也无法被工程方判定「这个新功能是否越界」。

**为什么值得做。** 目标受众是**企业安全与审计团队**。他们的第一个问题永远不是「你的功能是什么」，而是「你的威胁模型是什么」。这份文档是所有后续安全工作的判定基准——没有它，每次新增功能都要重新争论边界。**成本最低，公信力收益最高。**

**交付物。**
- 对手模型：能力清单（可读任意通道内容？可控制部分节点？可重放？可串通？）与**明确的排除项**。
- 信任边界图：宿主 / 插件 / 节点 / 模型 / 存储，各自的信任级别。
- 与 4 条「不防」一一对应的正式条目（把散文升级为可引用条目）。
- 每条边界配一个**可执行的判定问题**：「若新功能 X 引入，是否越过边界 Y？」——使其可被后续 PR 使用。

**风险。** 写得过于宽泛会变成免责声明；必须**具体到可判定**才有价值。建议每条边界都配一个现有测试用例作为锚点。

## 3. P1：保管策略一致性测试套件

**现状。** 宿主通过 `defineCustodyPolicy` 声明 `custody` / `extractClaims` / `describeArtifact`（见 [README](../README.md) §3）。这是一等集成点。

**缺口。** 现有集成测试已使用不同自定义 custody/extractClaims 策略覆盖13通道及可选字段，并非仅测试单一内置策略；但尚无可独立交付的宿主一致性套件。策略为 opt-in，检查只覆盖宿主提取器识别的 artifact 身份，不等于自然语言语义泄漏检测。套件应验证已声明的 claim 语法，不以有限测试声称证明任意提取器完备。

**为什么值得做。** 这是把「可证明隔离」从**声明**变成**可验证**的关键一步。宿主拿到一个套件，跑一遍，就知道自己的策略是否满足契约。这把集成从「凭信心」变成「可判定」，并且**不需要改任何生产代码**——套件是新增的测试资产。

**交付物。**
- 一个可被宿主独立运行的一致性套件，覆盖至少：未持有即拒绝、持有即放行、13 条通道逐一覆盖、可选字段（`messageId` / `dependsOn` / `retryOf`）不得成为隐式隧道、拒绝必须是原子的（不改网络状态、不扣配额、不留脏数据）。
- 每项给出**通过／失败的可读判据**，失败时指明是哪条契约被违反。
- 一份「如何为自己的策略运行该套件」的接入指南。

**风险。** 若套件要求宿主策略满足本仓库未公开的隐含假设，会把集成变成猜谜。设计时必须**只用 `defineCustodyPolicy` 已公开的契约**。

## 4. P1：跨网络隔离的证明与声明

**现状。** 全部状态按 `networkId` 隔离，每个网络有独立的串行原子 mutation 队列（见 [修复机制报告](REPAIR_IMPLEMENTATION_REPORT.md)）。多租户是首要目标场景（[战略白皮书](STRATEGY_AND_POSITIONING.md) §3.2）。

**缺口。** 已有 REVIEW-02 验证跨网络同号节点并行停止与资源释放隔离，尚缺所有协议引用与读取面的端到端补证。nodeId/taskId 是网络局部身份，可在不同网络重名；不能只靠字符串校验或 networkId 分区宣布租户隔离。observer 按传入 sessionId 找网络，ATN 层没有租户认证主体到该 session 的授权映射。

**为什么值得做。** 按 networkId 分区为网络业务隔离提供基础，读取认证与宿主资源授权仍须独立证明；结果可能要求修复代码或收窄声明。已有同号节点回归可作为起点，但不能据此预判无需新代码或成本必然可控。

**交付物。**
- 纯结构检查加真实 live Agent/RPC 集成验证：重名 nodeId/taskId、外部引用、artifact/message 的宿主命名空间、观察主体授权，各层分别判定；本地重名引用解析到调用者网络，不应一概作为外部引用拒绝。
- 若存在任何跨网络可达路径，逐条列出并评估。
- 一份网络绑定边界及宿主认证前提声明，纳入威胁模型（§2）；验证前不承诺「网络即租户」。

**风险。** 共享的宿主服务（存储域、凭据、模型路由）可能成为非 ATN 框架内的旁路——必须在声明中**明确划出 ATN 框架的边界**，不得声称覆盖框架之外。

## 5. P1：拒绝日志的持久化审计出口（含一个必须先解决的张力）

**现状。** 13 条通道有统一拒绝码，拒绝不提交 ATN 网络业务 mutation；`defineCustodyPolicy` 已有同步 `onRefusal(error,record,sender,operation)` 出口。该出口并非插件持久日志，宿主可记录；Harness 的会话/工具事件也不等于 NetworkRecord。不能将网络状态无副作用扩大为系统中完全没有日志。

**缺口（这里有一个真实的设计张力，值得单独指出）。**
- 「零持久化副作用」是为了**状态完整性**：一次被拒的请求绝不留下脏数据。这是正确的设计。
- ATN 没有自带持久拒绝 journal；宿主可通过现有 onRefusal 记录，但其持久性、完整性、访问权和故障处理尚无统一契约。
- 现有测试有拦截与状态不变证据，日志只能为完整性契约提供证据；缺少日志本身不证明未发生传输，有日志也不自动证明所有通道都被覆盖。

**为什么值得做。** 可复用现有出口设计审计契约；先明确拒绝分类、故障语义与内容最小化，再决定是否新增存储或 outbox。它不是合规交付的唯一途径，一致性套件与边界证明同样必要。

**必须先解决的设计问题。**
- 网络业务回滚与审计追加须分别定义一致性；同一 mutation 临界区不能让两个独立存储自动原子提交。比较单存储事务、宿主 durable sink/outbox 与显式丢失策略，规定 sink 失败及崩溃窗口。
- 拒绝的原因必须结构化到可被 SIEM 消费，同时**不得**把被拒内容本身写入日志（否则日志成了新的越权数据通道——这会自相矛盾）。
- 需要明确：审计日志是宿主资产还是网络资产？谁有读取权？这直接牵动 §2 的威胁模型。

**交付物（建议先出一份设计稿，再实施）。**
- 一份设计稿，明确上述三个问题的答案与理由。
- 结构化拒绝事件格式（JSON Lines）。
- 在限定 claim 语法、通道覆盖与日志完整性前提下的拦截证据工件；不声称证明所有语义数据泄漏均未发生。

**风险。** 这是本文中**最容易做错**的一项——把被拒内容写进日志会制造一个新的越权通道。设计稿必须先于实现，且必须经安全评审。

## 6. P2：多网络（舰队）观测面

**现状。** C 已完成结构化视图、可选 Tab API 注册与可用顶栏回退；完整 provider host 激活仍受上游阻碍，见 [C 报告](BETTER_SIDEBAR_IMPLEMENTATION_REPORT.md)。观察按单个 session/network 取数，任务及事件有界，没有全生命周期拒绝计数。

**缺口。** 多租户运营者的真实需求是**跨网络**的：哪些网络健康、哪些在产生拒绝、哪些节点在耗尽预算。单网络视图需要逐个点开。

**为什么值得做。** 这是本轮 UI 改造的**自然延伸**，且直接服务于多租户定位。better-sidebar 的 tab 框架天然支持这种「一个 tab 看全局」的形态。

**交付物。** 跨网络的汇总视图：网络清单、健康度、拒绝计数、预算消耗。必须保持观察通道**纯只读、不唤醒模型、零额外 token**。

**风险。** 跨网络聚合会引入一个**新的读取面**——它可能成为跨租户信息泄漏的通道（运营者能看到租户 A 和 B 的元数据）。**必须先与 §4 的跨网络隔离声明对齐**，明确聚合视图的授权模型。这一点如果不先想清楚，会把 §4 的成果反噬掉。

## 7. P2：harness 兼容矩阵与升级门

**现状。** 本轮精确锚定 Harness `0.2.1-alpha.2` 与其 Cordis `4.0.5-alpha.1`，旧 Desktop rc.2 CLI 拒绝新包。A 实测 guide 为24篇，C 另暴露 provider 服务名/peer 漂移；详见实施报告。发布标签随时间变化，不作为兼容性证据。

**缺口。** 每次 harness 发版都要人工逐条核对 20+ 篇 upgrade guide。这个痛点**已经被本轮证实是真实的**，而且会重复。

**为什么值得做。** 把一次性的手工劳动变成 CI 门。成本低（复用现有 `smoke:profile`），收益是长期的。

**交付物。**
- 一份兼容矩阵：本插件版本 × harness 版本 → 支持状态。
- 一个 CI 门：对声明的 harness 版本逐一跑安装 + smoke，任一失败即红。
- 一条策略：精确实测版本为发布阻断门；新版本/通道仅为前瞻探测，测试通过再扩展声明。增加可选 provider 缺失/存在/完整激活三层测试。

**风险。** 不得声明未经测试的 next 支持来规避 alpha 红灯；当前已声明的 alpha.2 必须阻断发布。可选 provider 接口通过不代表其 host 激活通过，两层状态必须分别显示。

## 8. P2：确定性重放与取证验证

**现状。** 网络记录是唯一原子持久化单元，持久化 domain 版本为 1。[信息边界文档](information-boundary/) 已有 `binding-before.json` / `binding-after.json` 这类「拒绝序列一致性对比」的先例。

**缺口。** NetworkRecord 没有完整拒绝序列，也不是完整输入事件 journal；binding-before/after 是确定性夹具对比，不是部署历史存证。仅凭终态记录不能重建全生命周期，更不能证明不可篡改。

**为什么值得做。** 有限的终态不变量校验可先做；完整重放须先收集确定性输入/策略版本/授权历史，抗篡改还需哈希链/签名及可信锚点。当前证据不足，不能将其评为低风险完整重放。

**交付物。** 先定义可恢复字段与不可恢复判定清单；审计 journal 契约建立后，再决定确定性重放器和独立完整性验证范围。不调用模型。

**风险。** 若记录本身不足以重建全部判定（例如依赖运行时的瞬时状态），必须**如实说明哪些判定不可重放**，不得声称完全可重放。

## 9. 明确不做

以下三项**不建议**投入，理由分别是：

1. **不做新的协作机制**（中心仲裁、声誉算法、复杂投票、白板回归）。这是 [战略白皮书](STRATEGY_AND_POSITIONING.md) §2.2 的第一条高压线，且十一轮实测已给出终局回答。
2. **不做速度／吞吐对比**。第二条高压线。分布式协作有固有信令开销；在没有隔离需求的场景下单智能体更直接。
3. **不做「更聪明的拓扑」**。项目已经明确放弃「自适应拓扑 → 更好的任务结果」这一箭头。动态出度（本轮）的定位是**让额度与规模匹配**，不是**提升任务正确率**——实施与宣传时都不得越过这条线。

## 10. 与现有路线图的关系

[战略白皮书](STRATEGY_AND_POSITIONING.md) §2.1 已列出的四个方向，本文的处理如下：

| 既有方向 | 本文的处理 |
|---|---|
| 更丰富的保管模型（只读 / TTL / 委托 / 撤销） | **保留**，建议排在本轮 P1 之后。它是保管层的能力扩展，但优先级低于「先能证明现有能力」 |
| 拒绝日志转化为合规产品 | **升级为 §5**，并指出其中必须先解决的设计张力 |
| 拓扑换边纳入策略管辖（Topology-as-ACL） | **保留**。与 §4（跨网络隔离）同属「谁能连谁」问题，建议**合并设计**，避免两套授权模型 |
| 对接真实数据权限底座 | **保留**，优先级不变。属集成工作，不阻塞信任轴主线 |

**核心判断：现阶段最大的缺口不是「能力不够多」，而是「已有的能力没有被形式化、没有被证明、没有被交付成可核验的工件」。** 因此本文把 P0/P1 全部放在补证与形式化上，而非新增能力。
