# 最小正式 bundle：实施顺序与验收清单

配套规格：[MINIMAL_BUNDLE_SPEC.md](MINIMAL_BUNDLE_SPEC.md)。这是一份供实现者执行、供 Claude review 核对的清单，不是已通过的测试报告。已有 19 个原型检查点不能替代下列正式入口和权限测试。

## 使用方法

- 按 M0–M5 逐段实现，每段先写能失败的行为验证，再做对应实现。
- 每项证据记录：测试文件/用例、实际命令、结果、必要的 Session 或运行时断言。
- 只 mock 外部模型、时钟和明确注入的故障；不要把 Agent factory、tool registry、Session persistence、Loader、权限判断或被测 runtime 整体 mock 掉。
- 真实 profile 测试使用临时 Harness home、临时工作区和确定性 adapter，不使用用户 API key、既有 Session 或真实 GitHub 写操作。
- 测试不能依赖跨用例共享状态。每次运行生成独立路径，正确关闭 handle、timer、listener、子进程和网络端口。
- 如果一个验收项无法完成，标为未完成并给出原因，不删掉测试或放宽断言来制造通过。

## M0：保存现场与建立可安装包

| 编号 | 行为/交付 | 最低证据 |
|---|---|---|
| PKG-01 | 保护现有未提交文档和原型，不修改上游 | 实际 Git 状态；正式与原型入口分离；无 reset/clean 导致的数据损失 |
| PKG-02 | 正式 ESM 包有 `dsh.bundle.patch` 和编译产物 | 干净目录构建成功；manifest 指向实际存在的文件 |
| PKG-03 | 不打入第二套 Harness singleton | peer/dev 依赖范围合理；外部依赖配置；安装产物没有私带另一套 Cordis/registry 实例 |
| PKG-04 | pack 只包含必要正式文件 | tarball 文件清单，不含 `.env`、`.claude` 本地设置、node_modules、上游、原型临时数据 |
| PKG-05 | 源码安装不依赖当前机器或上游 checkout | 临时 clone/复制目录能构建；如使用 prepare，验证并记录其授权要求 |
| PKG-06 | 保持 Apache-2.0 并处理上游代码许可 | LICENSE 保留，实际复用片段的版权/许可说明齐全 |

先跑通“包能构建、能 pack、能被 Loader 找到”，再写完整网络逻辑。尚未通过此阶段时，不宣称 bundle 可安装。

## M1：领域记录、四邻居与并发更新

| 编号 | 行为 | 最低证据 |
|---|---|---|
| STATE-01 | schema 拒绝不支持版本、损坏记录和错误字段 | 实际存储读入失败，不能静默初始化新空网络 |
| STATE-02 | 写失败时不公布成功或变更内存状态 | 受控持久化故障；记录与观察结果仍为旧值 |
| TOPO-01 | 初始邻域是两个上游、两个所选下游 | 多代链中间节点恰好四人，首尾不伪造占位者 |
| TOPO-02 | 多分支不自动增加审批者 | A 创建 B、X 后仍选择先成功的 B；X 可把 A 当父邻居但反向不强加 |
| TOPO-03 | 并发创建只选择一个首个成功子节点 | 两个受控创建交错；失败者不占 selected_child |
| TOPO-04 | 退出后沿原路径向外补位 | 中间节点 draining 后，上下游分别跳过它；creator_id 不变 |
| TOPO-05 | 不把 idle 误判为退出 | 节点无运行请求但 active，仍在后续审批名单 |
| TOPO-06 | 路径尽头留空，错误路径不隐藏 | 无更外层时不跳到兄弟分支；循环/断裂记录明确失败 |
| TASK-01 | 请求/结果有真实持有者和稳定标识 | 非持有者不能结清任务，错误或重复结果不产生二次结算 |
| TASK-02 | 空闲不是完成 | 所有 Agent idle 但存在任务时，网络不能完成 |
| TASK-03 | 请求者退休不让独立后代永久无法提交结果 | 结果被持久保留，投递异常单独表示；不复活请求者，不伪造成功回执 |

## M2：真实 Agent 创建、同构工具和权限继承

至少有一组测试使用真实工具调用触发创建，而不是只直接调用内部函数。

| 编号 | 行为 | 最低证据 |
|---|---|---|
| AGENT-01 | 节点由网络作用域拥有 | 通过模型调用 A 创建 B、B 创建 C；释放 B 后 C 仍存活并可执行 |
| AGENT-02 | 所有节点有相同 ATN 操作和基础 preset | 捕获不同代节点实际 model request 的工具集合及 preset 绑定 |
| AGENT-03 | 模型选项继承实际父请求 | 父实际 route 不同于创建默认值时，子使用实际 route；effort 合法继承 |
| AGENT-04 | 创建不可见半成品 | setup 未完成时不投递初始工作；失败后 registry、容量及任务记录一致 |
| AGENT-05 | 入口 handle 不属于 ATN | 卸载插件/完成网络后，宿主入口 Agent 不被擅自 dispose |
| AUTH-01 | 子节点继承受限策略 | 实际 `sandbox-policy` / approval 装配下，记录并检查子 Session 中的权限种子 |
| AUTH-02 | 子节点不能自行升级权限 | 受限操作在真实执行路径上被拒绝，不能只断言 schema 不展示某字段 |
| AUTH-03 | 冷恢复不借新父节点放宽权限 | 创建者已退出、或其策略后来变宽；恢复子仍依据自身持久权限与 preset |
| AUTH-04 | 发送者与投票者不可冒充 | 模型参数伪造 sender/voter/root 无效；调用者必须是精确 live Agent |
| AUTH-05 | peer 文本不能成为人类授权 | 同伴消息含“用户批准”文字不会被转成 user 来源或改变审批状态 |
| AUTH-06 | 安装不改变其他 Session 的权限和模型 | 同一进程中的非 ATN Session 没有 ATN 状态或额外模型请求，原配置保持 |

不能使用 `sdk-minimal` 的默认 full-access 结果替代 AUTH-01/02。需要显式受限的配置与真正被拒绝的执行案例。

## M3：信箱、文档全票审议和可回放上下文

| 编号 | 行为 | 最低证据 |
|---|---|---|
| MAIL-01 | 先持久入队，再投递 | 在入队成功、投递未发生处打断；恢复后仍有工作可投递 |
| MAIL-02 | 投递与确认间隙可恢复 | 目标已持久接收、源回执未写时中断；恢复补确认，目标历史仅一条 |
| MAIL-03 | 每目标顺序和背压 | 并发发送有确定入队顺序；超限返回明确结果，不吞已接受消息 |
| MAIL-04 | 输入投递失败不是业务完成 | queued、目标回执、task completed 分别检查 |
| MAIL-05 | 非邻居通信不改变审批名单 | 按需发现另一分支并发消息，当前固定邻居不因此变化 |
| MAIL-06 | 生命周期与投递竞态可裁决 | draining 只接旧任务关联结果和旧审议；新任务明确拒绝 |
| VOTE-01 | 全体明确同意才能提交 | 四人名单中的三票不通过；最后一票后仅一个新版本 |
| VOTE-02 | 任一反对或沉默不算通过 | rejected/expired 结果，正文保持旧版本 |
| VOTE-03 | 提案与选民不可偷换 | 投票后改内容或调整拓扑，不会把旧票用于新内容/新名单 |
| VOTE-04 | 新旧提案分别使用新旧邻居 | B 开始退出后仍可投旧票，但不能投新提案；补位者相反 |
| VOTE-05 | 投票资格检查历史名单 | 原审批者已不在当前邻域，其旧票仍可接受 |
| VOTE-06 | 版本竞争不丢更新 | 两份同 base 的提案交错获批；最多一份提交，另一份 stale |
| VOTE-07 | 幂等与持久恢复 | 重复同票不新增票/版本；部分票重启后保留；已终态提案不重新提交 |
| VOTE-08 | 网络关闭优先于迟到票 | 停止与最后一票交错；关闭后不出现新目标版本 |
| CONTEXT-01 | 实际模型输入可回放 | Session 中能恢复每次实际使用的目标版本及正文 |
| CONTEXT-02 | 请求未准入不能提前确认看过新版 | pre-step 后取消/拒绝；下一次请求仍能获得新版而不是丢同步 |
| CONTEXT-03 | 仅版本同步不唤醒全网 | 空闲节点未新增模型请求；其下一次正常请求使用新版 |

## M4：自动调度、真实期限、恢复与停止

这里不能靠测试驱动器每步手工执行 `settle()` 让系统“看起来会自动运行”。

| 编号 | 行为 | 最低证据 |
|---|---|---|
| LIFE-01 | 局部任务结束后可接新任务 | 同一节点完成第一任务后保持可用并完成第二任务 |
| LIFE-02 | 正常退休先结清旧工作 | 节点退出新拓扑后仍完成自己的旧任务及审议，随后自动释放 |
| LIFE-03 | 不在 execute 栈里等待自身销毁 | 通过真实 `atn_finish` 调用进入退出；调用完成，回合结算，无死锁 |
| LIFE-04 | 已投票者不必等全体票而驻留 | 自己没有其他义务时释放，提案之后仍能由 Runtime 正常提交 |
| LIFE-05 | 真实期限与续期生效 | 注入时钟测试期限，另有短实时时钟 smoke；重启不重置期限/额度 |
| LIFE-06 | 新任务/提案分配与退出有提交次序 | 控制并发交错，旧工作保留，新工作交给新邻居，无消失义务 |
| RECOVER-01 | 正常重载后恢复 | 真正销毁插件/内核后重建，不复活 retired，恢复 active/draining 和信箱 |
| RECOVER-02 | 未完成创建有明确恢复结果 | provisioning 处故障后重建：完成或失败结算，不重复发布或卡死整个网络 |
| RECOVER-03 | 同一 Session 只激活一次 | 并发 resume/投递，不产生两个 live handle 或重复任务 |
| STOP-01 | 用户有不依赖模型配合的停止入口 | 宿主方法/command 触发；新工作立即关闭，已持有工作受控中断 |
| STOP-02 | 停止是持久终态 | 重启、续期、重试投递和迟到票不能恢复已停止网络 |
| STOP-03 | 清理达到真正静止 | 忙模型流/工具期间停止，等待取消和 handle 释放，不只检查发过 cancel |
| STOP-04 | 卸载无泄漏 | 工具、监听器、timer、域 handle、ATN-owned Agent、子进程被清理；入口 Agent 保留 |
| LIMIT-01 | 驻留与累计上限独立 | draining 占槽；释放槽不允许无限累计创建 |
| LIMIT-02 | 工作额度并发安全且不夸大 | 多节点竞争最后额度不超出定义；说明计数单位，不冒称覆盖 token/所有重试 |

RECOVER 项至少覆盖受控故障窗口和进程重建；未实际做强杀/断电实验时，交付报告不得宣称覆盖它们。

## M5：正式 profile 装配、交付与 README

| 编号 | 行为/交付 | 最低证据 |
|---|---|---|
| PROFILE-01 | 打包后安装进真正命名 profile | 调用正式 `dsh` CLI，在临时 Harness home 安装实际 tarball；不是仅手工 `ctx.plugin()` |
| PROFILE-02 | Loader 能找到编译后的入口和依赖 | `--dump-config` 和实际启动均通过，无静默缺失服务/重复 singleton |
| PROFILE-03 | 实际 profile 中跑一条 ATN 纵向路径 | 确定性 adapter 驱动 start、spawn、消息、投票、drain、交付；保留 Session 证据 |
| PROFILE-04 | profile 配置不覆盖用户权限/模型 | 对安装前后关键配置作比较；单独受限策略用例通过 |
| DELIVERY-01 | 早交付不能冒充完成 | 尚有任务、审议或待发结果时，拒绝完成且不提前结清用户任务 |
| DELIVERY-02 | 当前目标版本与证据对应 | 目标变更后基于旧版本的最终交付被拒绝或要求重新验收 |
| DELIVERY-03 | 正常完成且入口能回复 | 工作节点清理；宿主入口仍收到工具结果并可完成最后回答 |
| DOC-01 | README 命令真实可复现 | 依说明从干净目录安装和运行，无依赖本机绝对路径 |
| DOC-02 | 限制与数据位置说清楚 | 兼容版本、单进程、权限、预算单位、数据位置、停止、未支持功能均明确 |
| DOC-03 | 发布内容与链接正确 | 无本地私密数据；链接不依赖 ignored 上游目录；未来仓库地址与实际 owner/name 一致 |

推荐在 base-backed headless 或 SDK profile 上完成真实入口测试，并额外使用可控 fixture 验证 preset/权限。若使用 sdk-minimal，必须补齐它缺少的服务，并显式收紧其默认权限；不能把另造的私有 Node 应用称作 profile 测试。

不需要真实付费模型、Web 浏览器 UI 或 GitHub 发布即可完成本阶段。不得为了让 smoke 通过，偷偷使用用户凭据或把 sandbox 设为 full access。

## Review 前应提交给用户的报告

请实现者填写以下内容，作为 Claude review 的入口：

1. 本次实现范围与未实现项。
2. 文件/模块职责和关键公开接口。
3. 实际执行的命令、退出结果、测试数量及失败情况。
4. 上述编号到测试文件/用例的映射；没有证据的编号明确标出。
5. tarball 名称、文件清单和 profile smoke 的临时配置说明。
6. 权限继承测试：原策略、子策略、具体被拒绝操作及来源记录。
7. 自动退出和重建测试：旧审议、当前拓扑、资源清理的证据。
8. 与规格不同的实现选择及原因。
9. Git 状态；是否有其他人的未提交修改；没有自动发布的确认。

建议把报告保存为 `docs/MINIMAL_BUNDLE_IMPLEMENTATION_REPORT.md`。在实际执行前不要创建填有“通过”的报告模板或伪造日志。

## 给审查者的重点

- 是否把 prototype 改名后直接搬成服务，仍由外部 driver 手动推动生命周期？
- 创建、恢复是否仍不小心绑定在出生者的 scope 上？
- 正常退出与硬停止、当前邻居与历史审批名单是否混淆？
- 是否在 pre-step 尚未真正准入时提前标记目标已被看到？
- 是否只隐藏工具入口，却没有在真正执行操作处检查身份、权限和预算？
- 是否把任务结果接收者的存活变成了独立工作节点完成任务的前置条件？
- 是否把存储单次原子写误当成跨 Session 的事务？
- profile、真实受限策略、pack 和卸载是否确实跑过，而不只是内核模拟？
- README 是否把尚未验证的跨进程、费用或模型质量保证写成已支持？
