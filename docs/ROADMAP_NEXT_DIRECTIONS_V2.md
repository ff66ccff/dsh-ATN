## 3. P0：威胁模型与读取面边界

**现状。** [README](../README.md) §"极致诚实"列出 4 条"不防"；[14 条通道审计](information-boundary/OUTBOUND_CHANNEL_AUDIT.md) 定义出站契约。**没有**独立的威胁模型文档（文档库内检索无此文件）。

**缺口（substrate 使之成为紧急）。** 当前有三条**读取面**，其暴露内容与授权依据各不相同，却都没有被形式化：

| 读取面 | 暴露内容 | 当前授权依据 |
|---|---|---|
| 模型工具 `atn_search` / `atn_visit` | `sub_task` / `artifact` / `rationale` / `refs` / `citedBy`（**不含**作者与权重） | 调用者是本网络节点（`requireCaller` 身份，非主体授权） |
| 观察快照 `atnObserver/snapshot(sessionId)` | 子任务文本（截断 512 字符）、**`authorId`**、权重、引用/被引计数、容量、步纪元、交付证据链（`src/observer.ts:253-259`） | 仅"能指名 sessionId"；描述符未声明 resource/principal（§4） |
| 宿主 API `exportSubstrate(networkId)` | **完整四字段、作者、权重、`citedBy`、证据链**（`src/runtime.ts:562`） | 无调用者校验；任何持有 `ctx.atn` 的宿主插件可导出任意网络 |

**为什么值得做。** 目标受众的第一份索要物就是威胁模型；而本轮 substrate 把"网络内的agent 文本"变成了可被读取、可被引用的实体，读取权限问题从此不可回避。**成本最低、公信力收益最高，且是 §4/§8/§9 的判定基准。**

**交付物。**
- 对手模型：能力清单（可读任意出站通道？可控制节点文本？可指名任意 sessionId？可装宿主插件？可串通？）与**明确排除项**。
- 信任边界图：宿主 / 插件 / 节点 / 模型 / 存储 / 观察客户端，各自信任级别与**谁有读取权**。
- 三条读取面逐一给出：范围内的授权规则、范围外的显式声明、以及锚定的现有测试用例（14 通道、live 身份、原子回滚、`SUBSTRATE-*`）。
- 每条边界配一个**可执行判定问题**：「若新功能 X 引入，是否越过边界 Y？」——供后续 PR 与 brief 直接引用。
- 把 4 条散文式"不防"升级为可引用条目（推理衍生、物理侧信道、合谋互通、网络外动作）。

**风险。** 写成免责声明即失去价值；必须具体到可判定。**不得**在本文中宣称"网络即租户"或"任意语义泄漏不可行"。

## 4. P0：观察与导出的读取授权（principal / resource 声明）

**现状。** `createObserverDescriptor()`（`src/observer-schema.ts:48`）声明 `invocation: { kind: 'direct' }` 与严格 codec，**未声明任何 resource / principal 语义**。观察方法按传入 `sessionId` 找网络（`src/observer.ts:209-212`），ATN 层没有"主体 → session"授权映射。`exportSubstrate(networkId)` 不校验调用者。

**缺口。** alpha.2→alpha.4 期间上游引入并落地了**网关访问控制与 principal/resource 模型**（判定只对非 owner 主体生效；未声明 resources 的调用解析为 `global`；`@Remote` 选项与 lookup/context 提供者支持 `resource`）。本插件既没有声明资源语义，也没有定义 operator 与 owner 的区分，因此：

1. 任何能到达网关 RPC 的客户端，只要指名 sessionId，就能读到该网络的 substrate 文本、作者与权重；
2. 宿主插件可用 `exportSubstrate` 导出**任意**网络的完整内容，没有任何显式授权点。

**为什么值得做。** 这在上一轮只是"未验证的开放问题"；现在（a）上游已提供执行机制，（b）substrate 使被读取的内容成为真正的租户数据，（c）它是 §8 读侧分区与 §9 舰队面的共同先决。**全部零模型。**

**交付物。**
- 在观察描述符上声明 resource/reader 语义（使用 alpha.4 协议提供的机制，而不是自造旁路），使非 owner 主体受网关策略判定；不得以版本号比较替代能力探测。
- 定义并实现 **owner / operator** 的读取边界：谁能看哪个网络的哪些字段（至少区分"网络内容"与"网络元数据"）。
- `exportSubstrate`：要么给出显式 operator 门，要么在威胁模型中把它写成明确的宿主信任假设（二选一，**必须有书面结论**）。
- 负例测试：非 owner 主体指名他人 sessionId / networkId 时必须被拒绝或降级，且**失败必须先留红灯**；不得放宽任何既有网关校验。

**风险。** 极易把"网关能拦"误当作"租户隔离已证明"。必须分别报告：ATN 层是否校验、网关层是否校验、以及两者之间的信任前提。不得声称覆盖 ATN 框架之外的宿主服务（存储域、凭据、模型路由）。

## 5. P1：宿主 custody 一致性套件

**现状。** `defineCustodyPolicy` 是公开一等集成点；仓库内已有多种自定义 extractor 的集成测试，但**没有可交付给宿主的独立套件**。

**缺口。** 通道已增至 14 条，引用准入新增三类（`msg:` / `task:` / `artifact:`）与"未装策略即拒绝 `artifact:` 引用"的语义。宿主今天无法用公开契约判定"我的策略是否满足 dsh-ATN 的要求"。

**交付物。**
- 一个宿主可独立运行的套件，覆盖：持有即放行 / 未持有即拒绝、**14 条通道逐一**、可选传输字段不得成为隐式隧道、拒绝原子性（不追加消息、不消耗地址、不改权重、不改步数、不留脏数据、不产生邮件或唤醒）、`artifact:` 引用在无策略时必须拒绝、`substrate-full` 不得静默驱逐。
- 每项给出可读判据与失败时的契约名。
- 接入指南；**只用公开 API 与宿主自报的 claim 语法**，不得依赖仓库内部结构。

**风险。** 套件若隐含未公开假设，会把集成变成猜谜；必须包含**故意不合格的宿主实现作负例**，证明套件真的能检出不合格。

## 6. P1：跨网络引用与地址命名空间补证

**现状。** 全部状态按 `networkId` 隔离，每网络独立串行 mutation 队列；已有 REVIEW-02 级别的"跨网络同号节点独立停止"证据。

**缺口。** substrate 引入第四类标识（`msg:<n>`，**网络局部**），且 `exportSubstrate`/观察面都按 networkId 取数。旧结论未覆盖：同号 `msg:` 地址跨网并存、`task:`/`artifact:` 引用跨网解析、观察与导出在"指名另一网络"时的行为。

**交付物。** 纯结构检查 + 真实 live Agent/RPC 集成矩阵：重名 nodeId/taskId/msg 地址、本地重名引用必须解析到调用者网络（不得一概按外部引用拒绝）、artifact 的宿主命名空间、两个认证主体读不同 session 的对照；发现路径先留失败记录再修。

**风险。** `networkId` 是分区键，不是认证主体。报告必须把"业务分区"与"读取授权"分别判定，验证前不承诺"网络即租户"。

## 8. P2：读侧可见性（need-to-know 分区）

**现状。** substrate 的准入是**写侧**：引用须存在／可见／真实持有（`ref-unresolved` / `ref-not-visible` / `ref-not-owned` / `custody-unavailable`）。**读侧没有分区**：能调用 `atn_search` 的节点可检索全网消息（除作者与权重被隐藏）。

**缺口。** [战略白皮书](STRATEGY_AND_POSITIONING.md) 的四个目标场景里有两个（多租户、严格知悉范围）直接要求"节点不该看到它不该看到的**内容**"，而当前 substrate 是全网可读。本轮 brief 有意把读侧留作第二阶段。

**为什么值得做。** 这是"保管层从写侧声称校验扩展到读侧可见性"的自然一步，与既有 custody 复用同一套宿主策略——**不与拓扑出度模型竞争**。

**交付物。** 按主体/节点/角色的读侧过滤策略接口（作用于 `search`/`visit`，并明确它与观察面/导出的关系）；过滤必须确定性、可重放、可关闭；负例测试证明被过滤内容既不出现也无法通过引用旁路推断（至少覆盖"引用被过滤地址"这一情形）。

**风险。** 过滤**改变论文机制语义**（论文假设全网可读），必须在偏离清单中新增一条并说明；不得把读侧策略变成新的发现来源；不得与 §4 的授权模型并行发展成两套判定（见 §13）。

## 9. P2：多网络（舰队）观测面

**现状与缺口。** 同 V1 §6：运营者需要跨网络视图（健康、拒绝计数、预算消耗），但跨网络聚合本身是新的读取面。

**先决条件。** 必须先完成 §4（读取授权）并纳入 §3；否则聚合视图会把租户 A 与 B 的元数据暴露给同一主体。保持只读、不唤醒、零额外 token。

## 10. P2：精确兼容发布门（engines.dsh 版）

**现状。** 兼容判定已由上游改写：**有 `engines.dsh` 时它单独决定，peer 范围被忽略**（依据 `plugin-compatibility.ts:57-80`）。声明为 `>=0.2.1-alpha.4 <0.3.0`，仅 alpha.4 实测，且该区间准入宽度大于字面直觉（§1）。

**交付物。** 兼容矩阵（插件版本 × harness 版本 → 支持状态）；一个 CI 门：对矩阵中每个"已支持"版本跑安装 + smoke，任一失败即红；策略条文写明"`engines.dsh` 的范围只写实测版本，未实测版本不得进矩阵"；可选 provider 的**安装 / API 注册 / 完整 host 激活**三层状态分别显示（第三层当前明确为未激活）。

**风险。** 不得用放宽 `engines.dsh` 的方式绕过红灯；不得把 provider 安装成功写成激活成功。
