## 2. 阶段顺序：A → B → C → D

**顺序不可调换。** 理由逐条如下，每条都是具体的、可核对的依赖，不是流程偏好。

### A 必须最先

1. **依赖基线是所有其它工作的前提。** 若在 A 之前做 B 或 C，之后提升依赖会让此前所有测试结论**失去意义**——你无法区分「B 改坏了」还是「新版本改坏了」。
2. **A 是唯一行为保持的阶段**，因此是风险最低的起点。它的成功标准就是「行为逐位不变」，这同时验证了测试套件在新依赖下**仍然在测同一件事**。
3. **A 会核对客户端模块系统的一条变更**（未标记 `<style>` 的归属规则）。C 沿用同一套样式注入方式，因此必须等 A 确认该路径在新版本下成立之后再动。

### B 必须在 C 之前

1. **B 改变 `status()` 向模型报告的上限语义**（从天花板变为当前有效值）。C 的结构化面板要展示节点状态（含配额余量），**必须渲染 B 之后的语义**。若 C 先做，面板会按旧语义写一遍，B 落地后必须重做。
2. **B 只动 host 半，C 只动 client 半。** 让 B 先落地意味着 C 是客户端最后的改动面，之后不再有 host 改动追着它改。

### D 必须最后

1. **D 要核对路线图的事实主张**，其中 P0 第一条是「B 已经让第 5 轮结构证明的输入失效」。**该结论只有在 B 落地后才能核实**，且 B 的 brief 第 4.6 节会产出逐 seed 的结论变化——这正是 D 的输入。
2. **D 的优先级判断依赖 B 的结果。** 若 B 导致大量 seed 的可达性结论翻转，D 的推荐顺序必须相应调整。

### 阶段之间的硬闸门

**每一阶段的全部命令绿灯之后，才允许开始下一阶段。** 禁止「A 差一个用例先开 B」。

理由：B 会让一批断言常量 4 的用例失败，A 会让一批依赖旧契约的用例失败。**若两者混在一起，失败信号无法归因**，而本轮三份 brief 都要求「修复前失败留档」——混做会让留档不可用。

## 3. 跨阶段共享不变式

以下各条**在 A、B、C 三个阶段中都必须成立**，任何一条被破坏即视为该阶段失败。它们散落在各 brief 的「必须保留的既有语义」里，此处集中列出以便统一核对：

1. 入口 Agent 由宿主拥有；完成、停止、退休都不 `dispose` 入口。
2. 网络记录是唯一原子持久化单元；「检查 + 修改」在同一 mutation 临界区内完成。
3. 边是单向的；出生谱系只作追溯。
4. 工具身份、发送者、投票者取自真实 live Agent。
5. 同伴文本不构成人类授权；请求者评价不构成宿主验收。
6. `stepBudget` 不得被宣称成 token、HTTP 请求或费用上限。
7. **同能力原则**：A/B/C 三阶段都不得改变任何节点的模型、工具集或权限。B 改的是**连接额度**，C 改的是**呈现方式**，A 改的是**依赖版本**。
8. 观察通道必须保持**纯只读**：绝不主动唤醒模型、不增加 token 费用、不写网络状态。
9. 持久化 domain 版本保持为 1。
10. **不新增、不删除、不重命名任何模型工具**；不改任何工具 schema。
11. 不删除已有测试，不降低断言强度。因语义变更必须改写的断言，**逐条给出理由**。
12. **不得把未测试内容写成已通过。**

### 4.2 要求

- 审计必须产出一张**单一表格**：`位置 → 旧声明 → 新声明 → 依据（哪个阶段、哪条测试）`。**不得**只列改了哪些文件。
- **不得留下任何一处仍在陈述旧声明。** 全部改完后必须重新 grep 一遍并附上结果：
  - `出度`、`≤ 4`、`上限 4`、`1–4`、`硬约束`
  - `拓扑图`、`连通图`、`atn-canvas`、`可视化ATN网络`
- 改写时必须保留**可核验性**：B 之后「默认规模（8 节点）下上限仍为 4」这一点必须写清楚，因为它是历史实验结论仍然有效的前提。
- **不得**为了省事而删除声明本身（例如直接删掉整段「出度硬顶控制」）。承诺要么被更新为真，要么被明确撤回并说明理由。

### 4.3 收口时机

**在阶段 C 完成后、阶段 D 开始前**统一执行。理由：B 与 C 都会改 `README.md`，分开改会反复改写同一段；且 C 会删掉图形与截图，声明审计必须在那之后才能给出最终文本。

## 5. 阶段 D：目标 4 的交付形态（**与 A/B/C 性质不同**）

目标 4 是「想下一步拓展方向」——**它不是实现任务，不要写成代码**。路线图已经写好，因此 D 的职责**不是重述它，而是核实并修正它**。

### 5.1 D 必须做的事

1. **核实路线图的事实主张。** 逐条核对 `ROADMAP_NEXT_DIRECTIONS.md` 中对当前代码的判断是否仍然成立（A/B/C 已经改变了代码）。**发现任何过期或错误的判断，必须指出并修正。**
2. **收口 P0 第一条。** 路线图的 P0 第一条是「B 让第 5 轮结构证明的输入失效，必须重导」。B 的 brief 第 4.6 节会产出**逐 seed 的可达性结论变化**。D 必须据此给出：
   - 哪些 seed 的结论发生了翻转；
   - 翻转是否严重到需要**回退或调整 B 的曲线**；
   - 若不需回退，重导工作应如何排入下一轮。
3. **给出下一轮的范围决策**，而不是优先级清单的复述。对选中的每一项给出：做什么、为什么是现在、**什么证据表明它比其它项更该先做**。
4. **明确列出不建议做的项及理由。** 尤其要说明哪些项虽然看起来有价值，但会越过 [`STRATEGY_AND_POSITIONING.md`](STRATEGY_AND_POSITIONING.md) §2.2 的两条高压线。
5. **指出路线图遗漏的方向。** 若 A/B/C 的实施暴露了路线图未预见的缺口，写出来。

### 5.2 D 的验收

- 产出一份**决策记录**（不是新的路线图副本），含上述 5 项。
- 事实主张的核实结果**逐条**给出「仍然成立 / 已过期，修正为 X」。
- 至少指出**一处**路线图中需要修正或补充的地方（若确实没有，必须说明为何没有，**不得为了交差而编造**）。

## 6. 停止条件（遇到即停下报告，不得自行绕过）

以下任一情况出现时，**停止该阶段并报告**，不要继续推进、不要顺手扩大改动面：

1. **A**：核对 upgrade guide 时发现某项破坏性变更要求**重写客户端注册方式**（而非只改依赖版本）。
2. **A**：`AgentPresets` 默认导出或 `PresetDefinition` 类型在 `0.2.1-alpha.2` 中已不存在，且无法用等价写法迁移。
3. **B**：动态曲线导致**大量 seed** 的结构可达性结论翻转（「大量」的判定由实现代理给出并说明依据）。
4. **B**：发现任何路径会因上限变化而**静默截断既有 `peerIds`**，且无法在「上限永不下降」之外解决。
5. **C**：实测确认把 `'betterSidebar'` 放进模块 `inject` 会导致服务缺失时 `apply()` 不运行，**且找不到安全的可选注入写法**——此时「保留回退」这一要求无法满足，必须报告而不是静默降级为硬依赖。
6. **任一阶段**：某条既有测试必须**削弱**而非改写才能通过。
7. **任一阶段**：发现必须把两个阶段的工作混在同一次提交里才能通过。

**报告格式**：停在哪一阶段、哪一条、实测证据（命令与输出）、已尝试的方案、建议的下一步。**不得补造证据，也不得把未验证内容写成已验证。**

## 7. 提交策略

- **一阶段一提交**，提交之间不混。提交信息沿用本仓库的 conventional 风格（见 `git log`）：`feat:` / `fix:` / `test:` / `docs:` / `chore(release):`。
- 每个阶段先提交**修复前失败测试留档**，再提交代码修复——这是本仓库的既有规范（见 `docs/information_boundary/PRE_FIX_RECORD.md` 与历轮 brief）。
- 阶段 C 的声明审计（第 4 节）作为**独立的一次 `docs:` 提交**，不与 C 的代码改动混在一起。
- 阶段 D 的决策记录作为**独立的一次 `docs:` 提交**。
