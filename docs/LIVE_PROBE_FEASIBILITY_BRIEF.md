# dsh-ATN 真实模型探针可行性门实施说明

这份文档交给实现代理执行。上一批 dsh-agy / Gemini 3.8 Flash medium 探针得到 0/5，全部在 120.0 秒撞墙。复核 artifacts 后可以确定：**该批的步数预算与调用上限都是充足的，唯一不足的是墙钟期限**；而且这个不足**在派发任何模型调用之前就完全可以算出来**，却没有任何机制去算。

本轮**不新增产品功能**，只做一件事：**让「这批探针在给定条件下是否可能完成」成为花模型调用之前的纯计算判定**，并把上一批无法归因的延迟口径先定死。在 4.1 与 4.2 完成前，**不得开始任何新的真实模型运行**。

实现代理在动手前必须先完整阅读本文件，并按第 9 节完成标准交付。

## 1. 基线（已独立复核）

- 工作区：`D:\dsh-ATN`，分支 `codex/release-ready`。
- `npm test` 为 **553 项 runtime／集成 + 14 项 UI，全部通过，0 跳过**（原始输出 `.artifacts/agy-validation/20261015/test.txt`，已复核）。
- 上一批探针（`docs/AGY_GEMINI_MEDIUM_PROBE_2026-10-15.md`）冻结条件：8 节点、链长 2、**每节点步数 12**、**每次运行调用上限 96**、输出上限 4096、已观测 token 准入阈值 400000、**期限 120 秒**、**provider 派发并发 1**、仅 phase-1 checkpoint、seed 17/31/45/59/73。
- 上一批结果（自 `report.json` 逐 seed 提取，五个 seed 一致）：
  - `stopReason: timeout`，`elapsedMs` = 120,036–120,080 ms（全部精确撞墙）。
  - `budget.issued` = 17–23，**`budget.denied` = 0**，`lastRejection: null`。
  - `metrics.totals.toolDurationMs` = **151 ms**（seed 17 全部工具耗时）。
  - `errors` = 0，`toolErrors` = 0；每节点 attempts = **2–4**（8 个节点全部）。
  - 每 seed 有 1–5 次 `aborted` attempt。
- **参考运行已给出可用的下界**（`docs/execution-evidence/agy-model-20261015/references.json`，五个 seed 完全相同）：

  | 字段 | 值 |
  |---|---|
  | `issuedModelCalls` | **0**（确定性，不调用模型） |
  | `actions` | **60**（全网动作总数） |
  | `maxNodeActions` | **8**（单节点最多动作数） |
  | `entrySteps` | 8 |
  | 两阶段 | 均 `passed: true` |

- 因此**在冻结条件与参考下界之间可以直接对照**：

  | 维度 | 参考下界 | 冻结预算 | 判定 |
  |---|---|---|---|
  | 单节点步数 | 8 | 12 | **充足**（余 4） |
  | 全网调用数 | 60 | 96 | **充足**（余 36） |
  | 墙钟 | 60 次调用 ÷ 并发 1 × 每次延迟 | 120 秒 | **不足** |

- 历史五臂对照条件（`docs/FIVE_ARM_COMPARISON_IMPLEMENTATION_REPORT.md:13`）：48 步／节点、384 次调用、4096 输出、800 万 token 阈值、**600 秒**。上一批在**四个维度上同时收紧 4–20 倍**，其中三个本已充足，只有期限致命。
- 延迟口径存在**未解歧义**：seed 17 的 `metrics.totals.modelDurationMs` = **876,033 ms**，是 120 秒墙钟的 **7.3 倍**。这只有两种解释，且指向不同的修复方向：
  - **(a)** 单次调用服务时间约 30 秒，时长在重叠／被取消的 attempt 上累加 → 应**延长期限**；
  - **(b)** `modelDurationMs` **含排队等待**，并发为 1 时 8 个 session 都排到期限被取消，故每个都显示约 119 秒 → 应**提高并发**。

## 2. 本轮要解决的核心问题

### 2.1 不可行的配置没有被任何机制拦下

上一批的 93 次 runner 调用、76 次实际派发**全部发生在一个从算术上不可能完成的配置里**。参考下界（60 次动作、单节点 8）与冻结预算（96 次上限、每节点 12）都在同一个 plan 里，两者一对照就能看出期限不足——但没有任何步骤做过这个对照。

这是本轮唯一必须解决的问题：**在花模型调用之前，用纯计算判定「这批条件是否可能完成」**。

### 2.2 延迟口径未定，导致修复方向无法确定

(a) 与 (b) 都支持「期限不足」这一结论，但修法相反：一个是延长期限，一个是提高并发。**在口径定死之前不能改任何参数**，否则是在猜。

### 2.3 因此 0/N 目前不可解释

在 2.1 与 2.2 解决之前，任何 0/N 结果都只能说明「配置不可行」，不能说明模型能力、拓扑收益或速度。上一批报告已正确地拒绝做这类声明；本轮要把「不可解释」变成「可解释」——**让失败发生在花调用之前**。

## 3. 目标

- **G1 口径确定**：`modelDurationMs` 的含义由**实测**确定（是否含排队等待），并在代码与报告中显式定义。
- **G2 可行性门**：存在一个**零模型调用**的纯计算门，输入为冻结条件 + 参考下界 + 每次调用延迟，输出为「可行／不可行」及完整算术。
- **G3 门能拦住**：把 G2 的门跑在上一批的冻结条件上，必须返回**不可行**，并指出**期限**是唯一不足维度、给出所需数值。
- **G4 门不空转**：同一个门必须对**充足**的维度返回充足（不得对一切都返回不可行）。这是防止门退化为橡皮章的负向对照。
- **G5 先门后跑**：G2 通过之前不派发任何真实模型调用；通过之后的运行其失败才是可解释的。
- **G6 零行为变更**：`src/` 运行时行为逐位不变；不重写已归档实验的 `sourceHashes`；不替换失败 seed；不为通过而换模型。

## 4. 必须实施的项目

### 4.1 确定延迟口径（G1）

要求：

- 用**实测**判定 `modelDurationMs` 是否包含排队等待。不得靠阅读代码推断后直接写结论。
- 在度量中区分三个时刻并分别记录，使「排队时长」与「模型服务时长」可分离：请求进入内核的时刻、实际派发到 provider 的时刻、settle（成功/失败/取消）的时刻。
- 在代码与报告中**显式定义** `modelDurationMs` 的口径，且该定义必须与实测一致。
- 若 `metrics.totals.modelDurationMs` 为跨 attempt 累加（可超过墙钟），必须说明累加规则，避免读者把 876,033 ms 误读为单次调用耗时。

验收测试（确定性、零付费模型）：

- 构造两个在并发为 1 时**必然排队**的 attempt，断言：两者的服务时长为**互不重叠**的区间，且排队时长非零、可单独读出。
- 断言分解可加：对每个 attempt，`排队 + 服务 + 收尾` 等于该 attempt 的总时长（允许显式声明的舍入）。
- 明确断言 `modelDurationMs` 的口径，并给出一个**能区分 (a) 与 (b)** 的用例：若口径含排队，则该值可以超过墙钟；若不含，则不可能超过。

> ⚠️ **不得静默改动已归档实验的 `sourceHashes`。** 度量代码（如 `experiments/telemetry.ts`）很可能被归档设计以哈希固定。实现代理必须先确认：新增字段是否改变被固定的哈希口径。若改变，则必须在报告中说明，并给出应对（例如把新口径放在新的度量模块中、或在归档侧显式登记新哈希并保留旧哈希的可复核路径）。**不得**为了让新度量通过而悄悄重写旧哈希。

### 4.2 可行性门（G2、G3、G4）

要求：

- 交付一个**纯计算**的可行性门：不调用模型、不联网、可在 CI 中重跑。
- 输入至少包括：参考下界的 `actions` 与 `maxNodeActions`、每节点步数预算、调用上限、期限、派发并发、**每次调用延迟（含来源标注）**。
- 输出必须包含：
  - 每个维度的**逐项判定**（充足／不足）与余量；
  - **唯一或主要的不足维度**（若有）；
  - 该维度的**所需数值**（例如「期限至少需要 X 秒」或「并发至少需要 Y」）；
  - 门自身的**假设与保守性说明**。
- **参考下界必须被当作下界，而不是需求。** 确定性参考是「可能完成」的必要条件，不是充分条件：真实模型通常比确定性策略**更**费动作。门必须显式声明这一点，并对真实需求施以一个**明确写出的余量**，不得把 60 直接当作 60 就够。
- 门必须在配置不可行时**拒绝启动**真实运行，并说明要改哪个参数、改成多少。

验收测试：

- **G3 回归测试**：把门跑在上一批的冻结条件（8 节点、每节点 12、上限 96、期限 120 秒、并发 1、参考 `actions=60` / `maxNodeActions=8`）上，断言：
  - 结论为**不可行**；
  - **步数维度判定为充足**（12 ≥ 8）；
  - **调用上限维度判定为充足**（96 ≥ 60）；
  - **期限维度判定为不足**，且给出的所需数值与所用延迟假设一致。
- **G4 负向对照**：另构造一组条件（例如把期限提高到门算出的所需值），断言门返回**可行**。若门对任何输入都返回不可行，该测试必须失败。
- **G4 边界对照**：构造一组「只有并发不足」的条件，断言门指出的是**并发**而非期限。此测试用于证明门能区分两个方向（对应 4.1 的 (a)/(b)）。
- 门必须对**延迟来源**做标注；延迟若来自历史批次，必须写明来自哪一批、哪个字段。**不得编造延迟。**

### 4.3 延迟的获取方式（含首次运行的鸡生蛋问题）

要求：

- 门需要「每次调用延迟」作为输入，但**首次运行前没有该批的实测延迟**。必须解决这个问题，且不得靠猜测。两种可接受的做法（择一或并用，必须说明理由）：
  - **(i) 历史外推**：使用已有真实批次实测的每次调用延迟作为输入，并**显式标注来源与可比性限制**（不同 provider／模型／档位的延迟不可直接互推，必须在输出中写明）。
  - **(ii) 标定后门控**：先派发**有界且明确计数**的少量标定调用以实测延迟，再据此门控完整运行。标定必须：声明调用上限、计入该批总消耗、其自身不构成任何能力或性能证据、且标定失败时不继续。
- 无论哪种，门都必须把延迟作为**显式输入参数**，不得内嵌为常量。

验收测试：

- 断言门在未提供延迟来源时**拒绝运行**（而不是取默认值）。
- 若实现标定模式：断言标定调用数有硬上限、被计入总消耗、且标定结果不影响任何能力判定。
- 断言更换延迟输入会改变门的结论（即延迟确实参与判定，不是装饰）。

### 4.4 只有在门通过后才重跑（G5）

要求：

- **4.1、4.2、4.3 全部完成并通过测试之后**，才允许开始新的真实模型运行。
- 重跑必须：**保持模型与推理档位不变**（用户指定的 `gemini-3.8-flash-tiered` / medium）；**只改门指出为不足的维度**；并在报告中逐项列出改了什么、门为什么认为这样够了。
- 不得为了让结果好看而同时放宽多个维度。若门指出多个维度不足，逐个说明。
- 重跑的条件必须与历史五臂条件**明确区分**（后者是 48 步／节点、384 次调用、600 秒），不得混入同一比较。
- 若门判定可行而运行仍然失败，**这次失败才是可解释的**，必须据此如实报告，并说明门在哪个假设上过于乐观。

验收测试：

- 给出门的输出（可行判定 + 算术）与随之冻结的新条件表，两者的数值一致。
- 断言模型标识与档位与上一批相同（可 diff 冻结条件表）。
- 保留失败 seed，不替换、不重跑替换。

### 4.5 报告完整性（G6）

要求，本轮报告必须补上上一批缺的部分：

- **显式写出正向结果**：`errors` = 0、`toolErrors` = 0、未触发限流（Step 5 的 seed 31 曾撞 `RATE_LIMIT`，本批未撞）、资源全部 `released`。
- **显式指出 runner 报告中的模板文本**（通用的「五 arms」解释）与本批实际只跑 adaptive 不符——上一批已做了这件事，本轮保持。
- 不得把未知 usage 写成零，不得把参考下界写成需求，不得把 0/N 写成能力结论。

验收测试：

- 报告中逐 seed token 表存在且与 artifacts 一致。
- 报告中包含上述四项显式声明。

## 7. 停止条件（遇到即停下报告，不得自行绕过）

1. 确定延迟口径需要改动被 `sourceHashes` 固定的文件，且无法在保留旧哈希可复核路径的前提下完成。
2. 参考下界的 `actions` **不能**作为真实模型所需动作数的下界（例如参考走了模型不可用的路径）。此时必须报告，**不得**另造一个代理指标顶上。
3. 门算出的所需期限或并发超出合理范围（例如所需期限超过历史五臂的 600 秒一个数量级），说明瓶颈可能不在期限而在别处——报告而不是直接照算放大。
4. 门无法区分「期限不足」与「并发不足」（G4 的边界对照失败）。
5. 标定模式若被采用，其调用数无法被硬性限制。

**报告格式**：停在哪一条、实测证据（命令与输出）、已尝试的方案、建议的下一步。**不得补造证据。**

4. 参考下界的 `actions=60` 是否为真实模型的严格下界**未验证**（见第 7 节第 2 条）。若不能成立，门的结论必须相应弱化。

## 11. 一句话提醒

本轮的产出不是「让探针通过」，而是**让失败发生在花模型调用之前**。如果门接好了但没人验证过它**既能拦住不可行、也能放过可行**，那它只是一个橡皮章——第 4.2 节的 G3 与 G4 两组对照缺一不可。
